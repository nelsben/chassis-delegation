## Why

A worker that edits a file outside its card says so with `[[amend v=1 scope+=<path> …]]`, and the mod applies it on the worker's word before verifying. That is deliberate: the amend discloses an edit the worker has already made, `forbid=` stays the hard boundary, and the card author's blind spots are what the worker's judgement covers (one card needed four such files its author did not know about, all correct). Some adopters will still want the lead to approve a widening, since Anthropic's guidance says another agent's message never grants approval. A repo option lets them tighten it; the default keeps today's behaviour. An earlier attempt on this card built "hold by default" and was stopped before it reported: discard anything it left.

## Done when

- A repo option `scopeAmends` with values `apply`, `new-files`, `ask`, default `apply`, wired the way `review` is: a row in hooks/lib/configtable.ts (group `Checking the work`, help text `Whether a worker's request to widen its scope applies on its word: apply, new-files (only new files beside ones in scope), or ask`), parsing in hooks/lib/repoconfig.ts (a value outside the three is named in the config errors and `apply` is used), and a `.claude-plugin/plugin.json` userConfig entry. The manifest default and the table default are both `apply`, so tests/node/configtable.node.mjs needs no new exception. The option count in tests/configcmd.test.ts goes from 59 to 60. `applyAmends` is unchanged and stays the master switch: with it off, every block is listed and none applied, whatever `scopeAmends` says.
- With `applyAmends` on, a hand-back `scope+=` block is decided by `scopeAmends`: `apply` appends it as today (row `amended: …`). `ask` holds every `scope+=` block. `new-files` appends it only when every path it names (a) does not exist at the brief's base (read-only git in the worker's tree, e.g. `git cat-file -e <base>:<path>`; a glob path never qualifies; a git error holds it) and (b) sits in a folder a scope entry already names: the folder of a listed file, or under the fixed prefix of a listed glob (scope `tests/review.test.ts` lets `scope+=tests/new.test.ts` through; scope `hooks/lib/**` lets `scope+=hooks/lib/new.ts` through; neither lets `scope+=hooks/lib/update.ts` through when that file exists at base); else it holds the block. A held block is not appended; the row says `amend needs approval: <block> (scopeAmends <mode>) — append it to <brief path> to accept, then dispatch verify=<sha>`, and the verify runs on the un-amended brief, as a `scope-=` block is held today. `forbid+=` applies on the worker's word in every mode; `scope-=`, `forbid-=`, `ignore+=` and the inside-a-forbid rule are unchanged.
- When a verdict refutes only on scope and every out-of-scope path it names is covered by a block held under `scopeAmends`, next= reads `approve the amend (append it to <brief path>), then dispatch verify=<sha>; or refuse it`: nothing is resumed or escalated, and the tier holds. Any other scope refute keeps today's next=. An amend block already in the brief (the lead appended it) applies as today in every mode, so approving is appending the block and re-verifying.
- Tests (red first in tests/hooks.test.ts: at base, with `scopeAmends: "ask"` in the repo file, a `scope+=` for an existing out-of-scope file comes back consistent with `amended:`): engine tests for `apply` (applied, consistent, as today); `ask` (held, the row's needs-approval line, refuted on scope, the approve-then-verify next=); `new-files` with an existing file (held), a new file beside a scoped file (applied) and a new file in an unrelated folder (held); and the lead appending a held block then `dispatch verify=<sha>` (consistent). `forbid+=` applies under `ask`. Pure cases for the folder and glob-prefix rule go in tests/brief.test.ts. Existing amend tests pass unchanged under the default.
- Docs: docs/contracts.md › Amend's `scope+=` row says `applied on the worker's word under scopeAmends apply (the default); new-files applies only new files beside paths in scope; ask holds every one for approval`, and one sentence above the table says `forbid=` is the hard boundary and `scope+=` discloses an edit already made. docs/configuration.md gets a `scopeAmends` row beside `applyAmends`. CHANGELOG.md `## Unreleased` gets an `### Added` entry naming the option, its three modes, the default and the new next=, tagged MOD-170.
