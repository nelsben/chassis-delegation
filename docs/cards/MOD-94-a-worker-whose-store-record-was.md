## Why

Issue #157: for five hours every spawn record was refused by the host's store cap, so the verdict tool said "no attempt recorded", no verifier ran and the brain verified six cards by hand. Issue #159: the same lost records opened a worker slot, so three workers ran with maxWorkers 2. MOD-89 keeps the store under the cap and says a refused write out loud, but the verdict and the slot count still depend on a write landing; this card makes them survive one.

## Done when

- LIVE COUNT (#159). The hook keeps its own in-memory set of the briefed workers it saw start in this process (agent id, label, attempt, tier, alias, resources, brief path, cwd), removed when that agent hands back, completes or its verdict lands. The live state that claimSlot, the resource hold, the status line and /delegation read counts a running agent in that set as a worker even when its spawn record does not read back from the store; the store stays the source for workers started in an earlier process. An engine test with a store that refuses every spawn and tasks write and maxWorkers 2 starts two briefed spawns, then shows a third queued (by dispatch and by the hook), not started.
- LEDGER AT SPAWN. When a briefed (not ad hoc, not a review) spawn starts, one row is appended to the session root's .delegation/ledger.jsonl through appendLedger, with a field that marks it as a spawn row (e.g. event: "spawn") and enough to verify the attempt without the store: task, subtask, attempt, budget, tier, alias, agentId, brief path, cwd or worktree, repo when it is another, purpose, and at. It goes through ledgerHas so a repeat writes nothing, and `ledgerFile` off skips it as it skips the verdict rows. Every existing reader of the ledger ignores a spawn row: latestVerdictRow in hooks/lib/mergecmd.ts, `/delegation accept`, the owed list, the card id allocation (a spawn row still marks an id as taken), and the dashboard; a test holds each of these unchanged with spawn rows present. docs/contracts.md (or wherever the ledger row shapes are named) documents the spawn row.
- VERDICT FALLBACK. When a hand-back (the SubagentHandback text, or a completed agent) arrives for an agent whose spawn record does not read back, the verifier runs anyway from the in-memory set, else from the newest ledger spawn row for that agent id (or that task's newest open attempt) plus the brief file it names. The verdict row is posted, the verdict ledger row is appended and the owed list moves exactly as when the record is there. The verdict tool, asked for a task with no store record, takes the same fallback (in-memory set, then the ledger spawn row plus the brief) before it answers no attempt recorded; it answers that only when none of the three has the task. Engine tests: (a) store refuses the spawn writes, the worker hands back, a consistent verdict row and verdict ledger row appear; (b) a fresh hook instance (empty memory, as after a reload) with a ledger spawn row and the brief on disk, the verdict tool for that task runs the verifier and returns its verdict; (c) no store record, no memory, no ledger row: the verdict tool still answers the noSuchAttempt line.
- SAID OUT LOUD. A verdict reached through the fallback says so once in the debug log and on the verdict's row tail, e.g. `(from the ledger: the store had no record)`, so the brain knows the store dropped it. No new option. The refused-write row and `/delegation` store lines from MOD-89 are unchanged.
- DOCS. CHANGELOG.md gets one entry under `## Unreleased` naming #157 and #159. docs/internals.md says where the live count and the verdict fall back from, and drops any Known issues line this fixes.
- GATES. The red tests fail on origin/main and pass at the head; validate, node and test are green. No change to hooks/lib/retention.ts behaviour: the ledger is a repo file, not the store.

## Review

Read the whole diff. Every spawn-record write also lands in the hook's memory (rememberWrite in storeSet), so a refused write still leaves the worker in liveState through spawnByAgent, and the slot count and resource hold hold. The spawn row is appended once per tool_use_id, is marked by event (verdict rows already take kind), carries no verdict, and the readers' tests show each one unchanged with spawn rows present. The hand-back and the verdict tool fall back to memory, then to the newest unjudged ledger spawn row plus its brief, and the verdict says which on its row. Limits accepted for now: a resume writes no spawn row, so after a reload only the attempt that spawned can be rebuilt from the ledger; and an ad hoc agent's result reads the ledger once (about 100 KB today). The ledgerFile description in docs/configuration.md still says one line per judged attempt; it goes with the #162 docs card. Accepted.
