## Why

With delegateOnly deny live here, the brain's merge pipeline "cd /Users/<name>/Documents/<repo>-MOD-8 && … rm -rf .claude-plugin/types && cp -R <root>/.claude-plugin/types .claude-plugin/ …" was refused as a source edit: bashWrites resolves a relative target against the session root, so ".claude-plugin/" after a cd into a worker's worktree looked like the repo's own manifest folder. Every write in that command was into a worktree outside the root. MOD-8 taught the lexer ~, $HOME, $PWD and same-command variables; it still does not know that cd moved the cwd. The design says worktrees are outside the brain's deny and the brain merges there by hand, so this blocks the brain's normal job. Probed on 2026-10-10 under deny: an absolute write into a sibling worktree passes, a 2>&1 redirect passes, quoted text passes, a cp with an in-root source passes, git checkout -b passes; refused are (1) a relative write after cd into a worktree, (2) ANY git commit, even `git -C <scratch repo outside the root> commit --allow-empty`, because delegateDecision treats the lexer's commit flag as an offending write regardless of folder or staged paths, and (3) `sed -i '' 's/a/b/' docs/cards/X.md` (BSD sed, empty backup suffix), because the lexer takes the empty word as the first file and the script as a file to write. The brain commits allowlisted things by design (a card's status flip, the repo file, a CHANGELOG move, the fold of a card into a worker's branch inside its worktree) and never commits source, so a commit must be judged by what it commits and where.

## Done when

- bashWrites tracks the working directory through a command: a cd <dir> (absolute, ~, $HOME, $PWD or a same-command literal variable, per MOD-8's resolver) in an earlier segment or the same segment's prefix changes the base every later relative target resolves against; cd with no argument or cd ~ goes to home; a cd whose target is unresolvable makes every later relative target unknown (not counted, no path)
- a relative target in a segment that is a subshell or runs after a cd inside parentheses is resolved against the base in force at that point, and the base is restored after the closing parenthesis; when the lexer cannot tell, the target is unknown
- git -C <dir> and tar -C / make -C forms do not change the base for later segments but their own relative paths are resolved against <dir>
- git commit is judged by where it runs and what it commits: the repo is the cwd in force (after any cd) or the -C folder; a commit in a repo outside the session root is never counted; in the root, the committed paths are read with the allowed read-only forms (git diff --cached --name-only, plus git diff --name-only for -a / -am / --all, plus any pathspecs on the command) and each is judged by isAllowedPath exactly like a written path, so a commit of only docs/cards/, .delegation/, .chassis-delegation.json, CHANGELOG.md or docs/ files is allowed and one that includes a source path is warned or denied naming that path; --amend with nothing staged and no pathspec counts no paths; the bare commit flag alone never denies
- BSD sed -i with an empty or any backup suffix given as the next word (sed -i '' …, sed -i .bak …) takes that word as the suffix, never as a file, and the script word is never a file; only the files after the script are written
- isAllowedPath is unchanged; a literal relative target with no cd is judged exactly as today
- README's delegateOnly paragraph says that cd is followed and that an unresolvable cd makes later relative writes uncounted; CHANGELOG entry
