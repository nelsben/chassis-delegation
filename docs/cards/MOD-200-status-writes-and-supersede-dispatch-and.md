## Why

GitHub is the ledger of planning, but today the mod only files and reads issues: merge finish prints the gh issue close lines for the brain to run by hand, and nothing records on an issue when a worker starts or a verdict lands, so the person has to remind the brain to keep GitHub current. This card adds exactly two write shapes on the landRepo (comment with a body file under .delegation/status/, and close with a --comment) and uses them from dispatch, the verdict, merge finish and a new supersede option on land. Project status is left to GitHub's built-in workflows (PR linked = In Progress, closed = Done): the mod writes nothing to the Project beyond the existing item-add, and no gh issue edit shape is added.

## Done when

- Two new exact shapes pass checkGhIssue in hooks/lib/allow.ts when allow.landRepo is set, both bound to that repo only: `gh issue comment <1-9 digits> --repo <landRepo> --body-file <file under <root>/.delegation/status/>` and `gh issue close <1-9 digits> --repo <landRepo> --comment <text not starting with ->`; extra arguments, another repo, a body file elsewhere, or landRepo unset are refused with the shape text. The MOD-7 issueRepo comment shape (debriefs) keeps passing. The allow.ts header comment lists the two shapes.
- Both shapes also pass while allow.merge (the merge context) is set, the way MOD-197 passes the one issue view: extend the merge-time exception beside isMergeIssueView (a close or a comment on the landRepo, exact shape, nothing else). isRemoteArgv still returns true for every other gh.
- New pure module hooks/lib/status.ts: statusFile(root, id, attempt, kind) names the body file `<root>/.delegation/status/<id>-attempt-<n>-<started|verdict>.md`; startedComment({id, attempt, budget, tier, alias}) returns one line like `attempt 1/2 started · standard sonnet · card MOD-200`; verdictComment(row) returns the verdict row text; superseded(newIssue, reason) returns `superseded by #<n>: <reason>` (reason omitted when empty). No I/O in that module.
- Dispatch: right after a briefed worker's started row is posted (postStarted in hooks/register.ts, kind started or respawned, not resumed), when the card's `issue:` field is a whole number (issueRef) and the session root's origin is a GitHub owner/name, the mod writes the started body file (redacted with the same rules land uses), sets landRepo, and runs the comment shape. A missing issue field means nothing is written and nothing runs. A failed comment adds one line `status: comment on #<n> failed: <stderr, 200 chars>` to the dispatch result and is never retried.
- Verdict: after a verdict row for a briefed task is appended (runVerdict path, consistent or refuted), the same for the verdict body file: the row text redacted, commented on the card's issue; same silence without an issue, same single failure line in the verdict result.
- Merge finish (the MOD-189/MOD-195 block in hooks/register.ts): when cardIssue and closeRepo are known, the mod runs the task close itself: `gh issue close <issue> --repo <closeRepo> --comment "merged in #<pr>"` (or `merged at <sha7>` without a pr); when siblings were read and every other sibling is CLOSED it also runs the parent close `--comment "all <k> tasks done"`. finishLines no longer lists a close line that ran; the finish result reports `closed #<n>` per close that succeeded, and for a close that failed it keeps the old printed line in the remote block with `(close failed: <stderr>)` after it, for the brain to run by hand. The parent-still-open comment lines (`# parent #n: k of m tasks still open`) stay as they are.
- land gains supersedes: the tool schema LAND_TOOL has an optional `supersedes` number (whole, 1 or more) and parseLandTool accepts it; /delegation land accepts `--supersedes <n>` and LAND_USAGE names it; parseLandArgs returns it. After fileOne succeeds and the project add is reported, landWith runs one close on the old issue: `gh issue close <old> --repo <landRepo> --comment "superseded by #<new>: <note or title>"` and reports `closed #<old> as superseded by #<new>`; a failed close reports the line tried and gh's error, and the new issue is still reported as filed. With dryRun the close line is printed and not run. The landed body of the new issue gets a line `supersedes: #<old>` under the note.
- Workers stay denied: tests/ghguard.test.ts gains a case asserting ghWrites still lists `gh issue comment` and `gh issue close`; hooks/lib/ghguard.ts is not changed.
- Tests: tests/allow.test.ts covers both shapes passing and at least four refusals each (wrong repo, extra arg, body outside .delegation/status/, landRepo unset) and the merge-context pass; tests/status.test.ts covers the pure module; tests/merge.test.ts covers finish running the task close and the parent close, the still-open case not closing the parent, and the failed-close fallback line; tests/land.test.ts covers supersedes parsing in both forms, the usage line, the close line after a successful file, and dryRun printing it.
- docs/guide.md: the land section describes supersedes as the way to change a task's scope (create the new issue, the old one is closed with `superseded by #n`; the mod never edits an issue), and the merge section says finish closes the task and, when it is the last, the parent, and comments on dispatch and verdict; docs/contracts.md lists the two new shapes beside the MOD-192 ones. CHANGELOG.md gains an `## Unreleased` heading at the top (above 0.9.34) with an Added entry for this card naming MOD-200.
